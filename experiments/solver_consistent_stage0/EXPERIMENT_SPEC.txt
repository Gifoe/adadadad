# 5. 三个核心模型

实现三个模型。

不要把第三方工作的名字错误地贴到近似实现上。

---

## Model A — Vanilla Recurrent Loop

名字统一：

`vanilla_loop`

输入经过 encoder 得到：

`H_0`

然后共享 recurrent block：

`H_{k+1} = B_theta(H_k)`

执行 K 次。

这里：

- 不输入 t；
- 不输入 dt；
- 不输入 total budget K。

K 是纯粹的重复次数。

注意：

不要人为乘 `1/K`。

它代表普通 recurrent-depth Transformer 的离散 recurrence。

---

## Model B — Step-Conditioned Recurrent Loop

名字统一：

`step_conditioned_loop`

不要在报告中把它称为“exact LoopFormer”。

这是一个受 LoopFormer 思想启发的、用于受控比较的 step-conditioned baseline。

状态更新：

`H_{k+1} = H_k + G_theta(H_k, t_k, dt_k)`

其中：

`t_k` 和 `dt_k`

通过同一个小型 conditioning mechanism 注入 recurrent core，例如：

- sinusoidal / Fourier encoding；
- small MLP；
- FiLM / additive conditioning。

不要增加明显参数优势。

uniform schedule：

`dt_k = 1 / K`

`t_k = k / K`

这个模型允许 reasoning rule 显式依赖 step size。

Stage-0 不加入 shortcut consistency loss。

---

## Model C — Step-Size-Independent Vector Field

名字统一：

`vector_field`

定义：

`dH/dt = v_theta(H, t)`

核心要求：

`v_theta`

只能访问：

- 当前 state H；
- continuous time t。

它绝对不能访问：

- dt；
- K；
- total number of steps；
- solver name；
- remaining NFE；
- schedule identity。

检查所有代码路径，防止这些信息通过 embedding、config 或 cache 泄漏。

Euler：

`H_{k+1} = H_k + dt_k * v_theta(H_k, t_k)`

这里的 `dt` 只属于 solver，不属于 neural network。

注意：

Transformer recurrent block 原本通常输出新的 hidden state。

如果用于 vector field，不要直接把：

`B(H)`

当作 derivative。

应明确设计：

`v_theta(H,t)`

输出 state derivative / residual direction。

必须检查数值尺度。

如果需要，可以加入一个固定或可学习但与 dt 无关的 global residual scale。

如果加入，记录并做统一初始化。

---

# 6. Numerical solver

不要调用复杂 ODE package。

Stage-0 手写固定步长：

- Euler；
- Heun；
- RK4。

这样可以精确控制 NFE。

统一定义：

**1 NFE = recurrent neural core 完整前向调用一次。**

Euler：

`1 NFE / integration step`

Heun：

`2 NFE / integration step`

RK4：

`4 NFE / integration step`

必须写单元测试验证：

- Euler N steps -> N NFE；
- Heun N steps -> 2N NFE；
- RK4 N steps -> 4N NFE。

同时用一个简单已知 ODE，例如：

`dy/dt = -y`

验证三个 solver 随步长减小误差下降。

这个单元测试只验证 solver implementation，不作为模型实验结论。

Model A：

执行 K 次 recurrence。

Model B：

使用 uniform schedule：

`dt = 1/K`

Model C：

训练时只使用 Euler：

`dt = 1/K`

不要在训练时使用 Heun / RK4。

# 17. Numerical convergence diagnostic

只针对：

`vector_field`

使用固定 diagnostic subset。

建立高精度 numerical reference。

建议：

RK4 with sufficiently fine steps，例如：

- 32 integration steps = 128 NFE

再与：

- 64 integration steps = 256 NFE

比较。

如果两者 endpoint difference 已远小于主要实验中的误差，可以使用较细者作为 numerical reference。

然后测试：

Euler steps:

`4,8,16,32,64`

Heun:

`2,4,8,16,32`

RK4:

`1,2,4,8,16`

记录：

`dt`

和：

`relative endpoint error`

绘制：

`log(error) vs log(dt)`

可以拟合 slope，但不要硬编码：

Euler 必须 = 1，
Heun 必须 = 2，
RK4 必须 = 4。

Transformer dynamics 未必处在理想 asymptotic regime。

这里只报告实际结果。

最重要：

**numerical convergence ≠ reasoning correctness**

报告中必须明确区分。

# 24. Stage-0 最终需要回答的问题

最后生成：

`STAGE0_REPORT.md`

不要只罗列数字。

按下面结构写。

## 1. Experimental setup

准确描述：

- data；
- model；
- training budget；
- evaluation budget；
- hardware；
- parameter count。

## 2. Does budget sensitivity actually exist?

重点回答：

对于 vanilla recurrent model：

- 3/5/7/12/16 unseen budgets 是否降低 accuracy？
- harmful flips 有多少？
- OOD depth 是否更严重？

对于 step-conditioned baseline：

- uniform / nonuniform schedule 是否导致不同结果？

不能只看 hidden-state drift。

必须判断 task-level consequence。

## 3. Does the vector field reduce this sensitivity?

比较：

- task performance；
- harmful flips；
- schedule sensitivity；
- solver disagreement。

同时确认：

- training-budget performance 有没有被牺牲；
- recurrent computation 是否真的有用。

## 4. Numerical behavior

报告：

- Euler / Heun / RK4；
- convergence curves；
- observed slopes。

但明确写：

numerical convergence itself does not establish improved reasoning.

## 5. Alternative explanations

主动检查：

- vector field 是否只是更新幅度更小；
- 是否只是 confidence 更低；
- 是否 recurrent core 根本没有贡献；
- 是否参数数目不同；
- 是否某个模型训练得更慢；
- 是否数据存在 shortcut；
- 是否变化来自 sequence truncation。

## 6. Decision

最后只允许给以下三种结论之一：

### GO

同时出现：

1. baseline 存在明确 task-level budget / schedule sensitivity；
2. vector field 有意义地降低这种 sensitivity；
3. 没有明显牺牲正常 budget 下的 accuracy。

### UNCLEAR

有迹象但 seed=0 不足，或 effect 太小。

此时建议运行 seeds 1/2。

### STOP

如果：

- baseline 本身基本不存在有害 sensitivity；

或者：

- vector field 只让 hidden states 更稳定，却没有 task benefit；

或者：

- vector field 明显牺牲正常 performance；

则明确建议停止，不要用更多复杂 loss 强行救项目。

# 25. 一个探索性的继续门槛

不要把下面数字当成论文 significance threshold，只作为决定是否值得继续花 GPU 的工程 gate。

如果 seed=0 出现以下模式，可以进入 3-seed：

- 至少一个 baseline 在多个 unseen budgets 或 OOD-depth 条件下出现明显的 task-level degradation；
- harmful flip 不是极低的偶发现象；
- vector_field 相比 baseline 明显降低 harmful flips；
- vector_field 在 K/NFE=4、8 上 accuracy 没有明显下降。

如果改善只体现在：

- JS；
- hidden distance；
- convergence slope；

而 accuracy / harmful flips 没改善，则不要自动继续。
